Problem Definition & Motivation

Limitations of Traditional Ticketing

Long Queues & Manual Delays

Physical ticket counters create long queues, high transaction delays, and limited booking flexibility.

No Seat Transparency

Customers lack real-time visibility into theatre layouts and cannot choose preferred seats interactively.

Race Conditions & Double-Booking

Lack of atomic transaction management allows multiple concurrent users to book the same seat simultaneously.

Poor Feedback & History

No unified portal for instant cancellation, dynamic seat restoration, or aggregate review calculation.

Project Objectives

Proposed Objectives & Key Features

Multi-Category Discovery

Seamless browsing and searching across Movies, Live Concerts, and College Fests.

Interactive Cinema Seat Map

Real-time visual seat matrix with dynamic multi-seat pricing calculation.

ACID Concurrency Control

Oracle SQL transactions ensuring absolute seat isolation and zero double-booking.

Instant Cancel & Ratings

One-click cancellation with immediate seat deallocation and dynamic 1-5 star reviews.

Requirement Analysis

Functional vs Non-Functional Requirements

Functional Requirements

  • User Registration & Login with bcrypt hashing
  • Admin event management (CRUD operations)
  • Live seat map selection & atomic checkout
  • Real-time booking cancellation & history
  • 1–5 star event rating submission & display

Non-Functional Requirements

  • Data Integrity: 3NF Normalization, PKs, FKs, Check constraints
  • Security: JWT tokens & role-based route middleware
  • Performance: Sub-second queries via connection pooling
  • Zero Reload: Optimistic DOM updates for fast UX
  • Concurrency: Transactional safety against race conditions
System Architecture

3-Tier Full-Stack Architecture

Presentation Tier (Frontend)

HTML5, CSS3 Grid/Flexbox, Vanilla ES6+ JavaScript. Features visual seat map & optimistic UI rendering.

Application Tier (REST Backend)

Node.js & Express.js. Implements JWT authentication, bcrypt encryption, and structured API routing.

Database Tier (Oracle 11g XE)

Oracle Database 11g XE. Thick Client Connection Pooling, 5 Relational Tables, PL/SQL Triggers & Sequences.

Database Design

Entities, Attributes & Keys

1. USERS : user_id (PK), name, email, password_hash, role, created_at 2. EVENTS : event_id (PK), title, category, event_date, event_time, location, price, total_seats 3. BOOKINGS : booking_id (PK), user_id (FK), event_id (FK), client_id, total_price, booking_date, status 4. BOOKING_SEATS : (booking_id, seat_number) Composite PK, booking_id (FK) [Normalized 3NF Table] 5. RATINGS : rating_id (PK), booking_id (FK), event_id (FK), rating (1-5), rated_at

Key Design Rationale: Rather than storing booked seats as a comma-separated list, `BOOKING_SEATS` is normalized into an associative entity with a composite primary key, fully satisfying 3NF.

Database Model

Entity-Relationship (E-R) Model

┌───────────────┐ ┌───────────────┐ │ USERS │ ─── (1 : N) ───> │ BOOKINGS │ <─── (1 : N) ─── ┌───────────────┐ │ [user_id: PK] │ │[booking_id:PK]│ │ EVENTS │ └───────────────┘ └───────┬───────┘ │[event_id: PK] │ │ └───────┬───────┘ (1 : N) │ (1 : N) │ ▼ ▼ ┌─────────────────┐ ┌─────────────────┐ │ BOOKING_SEATS │ │ RATINGS │ │[booking_id,seat]│ │ [rating_id: PK] │ └─────────────────┘ └─────────────────┘

• USERS (1) places BOOKINGS (N) • EVENTS (1) has BOOKINGS (N) • BOOKINGS (1) reserves SEATS (N) • BOOKINGS (1) rates (1:1) RATINGS

Database Integrity

Normalization & Constraint Enforcement

Normalization (1NF → 3NF)

  • 1NF: Atomic attributes; eradicated repeating seat arrays.
  • 2NF: No partial dependencies on composite keys.
  • 3NF: No transitive dependencies; clean entity isolation.

Integrity Constraints

  • Primary Keys: Unique IDs on all core tables.
  • Foreign Keys: Enforces referential integrity.
  • Check Constraints: `role IN ('admin','user')`, `rating BETWEEN 1 AND 5`.
  • Triggers & Sequences: Automated auto-increment.
